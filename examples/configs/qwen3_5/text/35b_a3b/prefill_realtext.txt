The processing unit at the centre of this system keeps every intermediate tensor in local scratchpad memory, so a decoder layer can finish without ever writing back to main memory. That single decision shapes the rest of the design. Weights are laid out ahead of time in the exact order the compute units read them, activations are tiled to fit the scratchpad budget, and small kernels are batched together so the queue is never idle between them. Debugging such a machine is mostly an exercise in patience: a wrong address looks exactly like a wrong number, and a stale cache line looks exactly like a race. The tools that help most are the boring ones, a dump of the allocator state, a trace with real cycle counts, and a reference implementation on the host that is slow but obviously correct. When the two disagree, the interesting question is never which one is faster; it is which assumption differs. Most of the time the answer is an alignment rule that was true last month, a padding row nobody accounted for, or a buffer that two subsystems both believed they owned.

A test that only compares the words a model produces will call that a failure. A checkpoint that no longer matches the code, an environment variable read once at start-up and then changed, a reference file generated from inputs nobody recorded, a test that runs and asserts nothing: none of these announce themselves either. They are found by asking, of every green result, what exactly would have had to go wrong for it to be red, and being unsatisfied when the answer is difficult to state. A suite whose green is not falsifiable is decoration. Buffers that persist across a replay must be declared where the framework can see them, because a temporary that survives one forward and is recycled before the next produces output that is correct the first time and wrong afterwards. That failure mode is worth naming carefully: it is invisible to a single-shot test, it reproduces only with a warmup, and it looks exactly like a numerical problem until someone prints an address. Whenever a report says the first run passed and later runs did not, the address is the first thing to look at, before any tolerance is adjusted. Scheduling has its own version of the same lesson. Work is cheap to start and expensive to synchronise, so a plan that issues fewer, larger pieces usually beats one that issues many small ones, even when the larger pieces waste a few rows at the end. The cost of a launch does not shrink with the amount of work inside it, and once that is measured rather than assumed, several arguments about padding resolve themselves. Pay for a row when it buys a launch; never pay for a row to make a table look tidy. Evenness is worth pursuing only where it is free, and it is free more often than people expect, because the planner is already choosing among candidates that cost the same number of launches. What remains after all of this is bookkeeping, and bookkeeping is where most of the real defects hide. A checkpoint that no longer matches the code, an environment variable read once at start-up and then changed, a reference file generated from inputs nobody recorded, a test that runs and asserts nothing: none of these announce themselves either. They are found by asking, of every green result, what exactly would have had to go wrong for it to be red, and being unsatisfied when the answer is difficult to state. A suite whose green is not falsifiable is decoration. The remedy is dull and effective: record the inputs beside the outputs, make the failure mode explicit in the message, and prefer a check that reacts to the magnitude of a difference over one that reacts only when the difference crosses a threshold nobody chose deliberately. None of this is specific to one machine. The habits transfer: measure before arguing, write the measurement down next to the decision it justifies, and treat every number older than the code it describes as a question rather than an answer. A team that does this accumulates a record it can trust, and the record is what makes the next change cheap. A team that does not accumulates confident sentences whose evidence has quietly expired, and pays for them later at the worst possible moment, usually while something is on fire and nobody can remember which of the comfortable assumptions was actually checked. It helps to keep a short list of the things that are true only by coincidence, because those are the ones that break silently when an unrelated detail moves. Two quantities that happen to be equal today are not the same quantity, and code that relies on the equality will keep working right up until the day one of them changes for a reason nobody connected to it. The cure is not more defensive checks; it is writing down which of the two you actually meant, so the next reader can tell whether an equality is a definition or an accident. Similarly, a limit that has never been approached is not a tested limit, and a path that exists only in a fallback branch is not a supported path. Both should be labelled as such rather than counted as coverage. When the labels are honest, planning becomes arithmetic instead of debate, and the arguments that remain are the ones actually worth having.
